# 온라인 대전 — 트러블슈팅 경험 기록

만들면서 실제로 부딪힌 문제들을 시간 순서대로 남긴다. 각 항목은 **상황 → 증상 → 원인 → 해결 → 교훈**.
"됐다!"까지 가는 길이 대체로 한 번에 안 뚫렸기 때문에, 그 과정을 경험적으로 적어둔다.

---

## 0. 시작점 — "오라클 클라우드 계정을 만들었어!"

로컬 패스앤플레이(스피드·턴제)는 이미 됐고, 진짜 하고 싶던 건 **다른 기기끼리의 실시간 대전**이었다.
무료 서버(Oracle Cloud Always Free)를 확보하면서 착수. 아키텍처 인터뷰에서 세 가지를 정했다:
**턴제 1:1 / 방 코드 매칭 / Node + Socket.IO**. 정답은 절대 클라가 들지 않는 **서버 권위**로.

여기까진 계획대로였다. 문제는 그 다음, **"코드는 됐는데 왜 상대에게 안 닿지"** 부터 시작됐다.

## 1. wss가 안 붙는다 — iptables REJECT 순서 함정 (배포 최대 고비)

**상황.** 서버를 VM에 올리고 Caddy로 자동 TLS(Let's Encrypt)를 걸었다. 로컬에선 잘 되는데
공인 도메인으로는 인증서 발급조차 실패.

**증상.** Caddy가 인증서를 못 받는다. 외부에서 80/443 접속이 먹통. `curl`이 그냥 물린다(타임아웃).

**원인.** VM의 `iptables INPUT` 체인에 **`REJECT` 규칙이 80/443 `ACCEPT`보다 위(앞)**에 있었다.
Ubuntu 기본 규칙이 5번째쯤에서 "나머지 다 거절"을 하고 있었고, 우리가 추가한 80/443 허용이 6·7번째로
**REJECT 뒤에** 붙어서 영영 도달하지 못했다. 규칙은 위에서부터 매칭되므로, 거절 뒤의 허용은 죽은 규칙.
Let's Encrypt HTTP-01 챌린지가 80으로 못 들어오니 인증서 발급이 실패한 것.

**해결.** 허용 규칙을 **REJECT 앞으로** 끼워 넣었다.
```
sudo iptables -D INPUT 7      # 잘못 붙은 443 허용 제거
sudo iptables -D INPUT 6      # 잘못 붙은 80 허용 제거
sudo iptables -I INPUT 5 -p tcp --dport 443 -j ACCEPT   # REJECT(5번) 앞에 삽입
sudo iptables -I INPUT 5 -p tcp --dport 80  -j ACCEPT
```
(Oracle은 이와 **별개로** Security List/NSG에서도 80/443을 열어야 한다 — 방화벽이 이중이다.)

**교훈.** 클라우드 방화벽 문제는 **두 층**을 의심한다: 클라우드 콘솔(Security List/NSG) **그리고** 인스턴스
OS의 iptables. 그리고 iptables는 **순서가 곧 로직**이다. "규칙을 추가했는데 안 되면" 추가 위치가
거절 규칙 뒤인지부터 본다. `sudo iptables -L INPUT --line-numbers`로 번호를 보고 `-I`로 앞에 꽂는다.

## 2. "다 고쳤는데 라이브가 그대로다" — Vercel 자동배포가 끊겨 있었다

**상황.** 서버도 붙고 클라도 고쳤는데, 실제 배포된 사이트엔 변화가 없다. 몇 번을 커밋해도 그대로.

**증상.** `git push`는 성공. 그런데 Vercel에 새 배포가 안 뜬다. 즉 **세션 내내 한 작업이 하나도
라이브에 반영되지 않고 있었다.**

**원인.** Vercel↔GitHub 연동이 **7월 14일경 끊겨** 있었다. 그 뒤의 푸시는 아무 배포도 트리거하지 않았다.
(이걸 모르고 한동안 "왜 안 바뀌지"를 코드에서 찾았다.)

**해결.** Vercel 프로젝트 Settings → Git에서 GitHub를 **다시 연결**. 이후 빈 커밋으로 배포를 강제 트리거해
파이프라인이 살아있는지 확인.

**교훈.** "고쳤는데 안 바뀐다"의 1순위 용의자는 **코드가 아니라 배포 파이프라인**일 수 있다.
증상이 "전부 반영 안 됨"처럼 광범위하면 코드보다 **파이프라인/연동 상태**를 먼저 확인한다.
배포 성공 로그(대시보드)를 눈으로 보는 습관.

## 3. 커밋 작성자가 엉뚱하다 — 저장소 로컬 Git 신원 오버라이드

**상황.** 커밋을 쌓다 보니 author가 의도한 신원과 달랐다.

**원인.** 이 저장소에 **로컬 Git 설정**(`user.name`/`user.email`)이 오버라이드로 박혀 있어 전역 신원을 가렸다.

**해결.**
```
git config --local --unset user.name
git config --local --unset user.email   # 전역 신원 상속
```

**교훈.** 커밋 신원이 이상하면 `git config --local --list`부터. 신원은 **하드코딩하지 말고 저장소 설정을
그대로** 쓰되, 로컬 오버라이드가 전역을 가릴 수 있음을 기억.

## 4. 무승부·패배 화면이 "상대가 나갔어요"에 가려짐 — 렌더 우선순위 버그

**상황.** 정상적으로 승부가 났는데(무승부/패배), 결과 화면 대신 엉뚱하게 "상대가 나갔어요"가 떴다.

**원인.** 종료 렌더 분기에서 **`oppLeft` 검사가 `over`(결과)보다 먼저** 걸렸다. 게임이 끝나면서
상대 소켓 상태가 잠깐 흔들리면 `oppLeft` 쪽으로 새어 결과가 가려졌다.

**해결.** 우선순위를 뒤집었다 — `if (oppLeft && !over)`로 **결과가 있으면 결과를 우선** 표시.
아울러 `resetRound`에 `setOppLeft(false)`를 넣고, 게임 종료 후 상대가 나간 경우엔 "재대결 불가" 안내를 붙였다.

**교훈.** 여러 종료 상태(정상 종료 / 상대 이탈 / 끊김)가 겹칠 수 있는 화면은 **표시 우선순위를 명시**한다.
"둘 다 참일 때 무엇을 보여줄 것인가"를 분기 조건에 못 박아야 한다.

## 5. 세븐세그먼트가 평문 숫자로 회귀 — 리팩터 중 유실

**상황.** 턴제 입력 슬롯의 숫자가 어느 순간 LED(`Seg7`)가 아니라 밋밋한 `{d || '·'}` 텍스트로 나왔다.

**원인.** 대전 화면을 손보다가 슬롯 렌더가 옛 형태로 되돌아갔다(리팩터 중 유실).

**해결.** `slot cell` + `<Seg7 char={d} />` 형태로 복구. 입력칸·키패드·기록 숫자는 **전부 `Seg7`**이라는
규칙을 다시 확인.

**교훈.** 디자인 시스템의 "모든 숫자는 Seg7"처럼 **불변 규칙**은 문서(CLAUDE.md)에 적어두고, 리팩터
후엔 그 규칙 위반이 없는지 훑는다. 시각 회귀는 타입 검사로 안 잡힌다.

## 6. "모바일에서 자꾸 끊겨" — 재접속 시스템 도입

**상황.** PC끼리는 잘 되는데 **모바일로 하면 연결이 잘 끊긴다.**

**원인.** 모바일 브라우저는 백그라운드로 가면 소켓을 끊고 타이머를 얼린다. 그런데 초기 서버는 소켓이
끊기면 **방을 바로 삭제**했다. 잠깐 화면 전환만 해도 방이 날아갔다.

**해결(1차).** 재접속 인프라를 깔았다.
- 서버: 끊겨도 즉시 삭제하지 않고 **유예(grace) 타이머**(처음 30s)를 두고, 그 안에 오면 이어감.
  플레이어에 `token`·`connected`·`graceTimer` 필드 추가.
- 재합류 `rejoin(code, index, token)` → 서버가 소켓을 원래 자리에 다시 연결하고 `resume`으로 상태 동기화.
- Socket.IO를 관대하게: 폴링 폴백, `pingTimeout` 40s. 클라 `reconnectionAttempts: Infinity`.
- 프론트: `opponentDisconnected`/`opponentReconnected` 알림과 `NetStatus` 배너.

**교훈.** 모바일 실시간은 **"끊김은 정상"** 전제로 설계한다. 끊김을 곧 종료로 보면 안 되고, **유예 + 재합류**가
기본기다. 이건 시작일 뿐이었다(→ 8·9번에서 더 깊이 파고든다).

## 7. 새 버전이 반영이 안 돼 / 업데이트 팝업이 거슬려 — PWA 전략 변경

**상황.** PWA로 설치해 쓰는데 새 버전이 잘 안 붙는다. 초기엔 "업데이트가 있어요" 팝업을 띄웠는데 거슬렸다.

**원인.** 서비스워커 업데이트를 수동 프롬프트로 처리하고 있었다. 모바일/설치앱은 자동 업데이트 확인이
잘 안 돌기도 한다.

**해결.** `registerType: 'autoUpdate'`로 전환. **팝업 없이** 새 버전은 백그라운드에서 설치되고
**다음 실행 때 적용**. 진행 중 강제 리로드는 하지 않는다(온라인 대전 끊김 방지). 앱이 보일 때마다
(`visibilitychange`) + 1분마다 `registration.update()`로 확인.
주의: 서비스워커 교체는 **한 텀 늦다** — 새 로직은 그 버전이 올라온 *다음* 실행부터 적용된다.

**교훈.** 실시간 세션이 있는 앱에서 **진행 중 강제 리로드는 금물**(대전이 끊긴다). "조용히 다음 실행에
반영"이 안전. 그리고 SW의 한 텀 지연을 계산에 넣어 테스트한다(방금 올린 게 지금이 아니라 다음에 뜬다).

## 8. "방이 만료됐는데 나는 계속 대기중" — 갇힘 상태 탈출

**상황.** 연결이 끊겨 방이 만료됐는데, **나(호스트)는 여전히 로비에서 "상대 대기중"**에 갇혀 있었다.
상대는 그 코드로 못 들어온다.

**원인.** 호스트 소켓이 끊김 → 30s 유예 뒤 방 삭제. 그런데 호스트 **클라이언트**는 소켓이 재연결되고
`rejoin`이 실패로 판정날 때까지 로비 화면에 그대로 남아 "대기중"처럼 보였다. 재연결이 느리거나 실패하면
그 상태가 길게 이어졌다.

**해결.** 재접속 실패(방 유예 초과·삭제) 시 **대기 상태에 갇히지 않게 메뉴로** 보낸다 —
"방이 만료됐어요. 다시 만들거나 코드로 입장해주세요." 로비에선 상대 끊김 배너 오표시도 막았다.

**교훈.** 재접속은 "성공/실패" 두 갈래를 **화면 상태로 반드시 소화**한다. 실패했는데 화면이 옛 상태로
남으면 사용자는 "멈춘 것"으로 느낀다. 실패 경로에 **명확한 탈출구(메뉴 복귀 + 이유 메시지)**를.

## 9. 핵심 난제 — 백그라운드 이탈 → "상대 나감" + 재입장 "방이 가득 참"

세션에서 가장 오래 붙든 문제. 사용자 리포트가 정확했다:

> "폰에서 방에 들어갔다가(게임 중에도) 다른 앱을 켜거나 백그라운드로 넘어가면 연결이 끊기고
> **상대가 나갔다고 뜬다.** 근데 그 코드로 **다시 들어가려니 이미 방이 가득 차 있다**고 한다."

**증상.** ① 백그라운드 갔다 오면 상대에게 "상대 나감"이 뜬다. ② 돌아온 내가 **코드로 재입장(join)**하면
"방 가득 참" 거절.

**원인(두 겹).**
1. **세션이 메모리(useRef)에만** 있었다. 탭이 리로드/종료되면 코드·자리·토큰이 사라진다 → 자동 `rejoin`
   불가 → 사용자는 어쩔 수 없이 **수동 `join`(코드 입장)** 을 시도. 그런데 방엔 내 자리(끊긴 채)와 상대,
   **2자리가 이미 차 있어** join이 "full"로 거절된다. (join은 토큰 인증이 없어 내 자리를 되찾지 못한다.)
2. **유예가 30s**로 짧아, 모바일이 조금만 오래 백그라운드면 방이 삭제돼 상대가 "나감"을 봤다.

**해결(2차 — 세션 영속 + 유예 확대).**
- **세션을 `sessionStorage`(`nb_online_session`)에 저장** → 탭이 리로드/복귀해도 마운트 시 복원해
  **자동 `rejoin`**. 그동안 "방에 다시 연결하는 중" 화면을 띄우고, 9s 타임아웃 폴백으로 메뉴 복귀.
  (수동 join이 아니라 **토큰 rejoin**으로 원래 자리를 되찾으니 "full" 문제 자체가 사라진다.)
- 나가기·방 만료·상대 이탈 시엔 세션 삭제.
- **서버 `GRACE_MS` 30s → 90s.** 모바일 백그라운드가 길어도 방을 유지, 조기 "상대 나감"을 줄임.

**교훈.** 재접속의 진짜 열쇠는 **세션 영속**이다. 메모리 세션은 "빠른 재연결"엔 통해도 "탭이 죽었다
살아나는" 모바일 현실엔 무력하다. 그리고 **재입장은 반드시 인증된 rejoin으로** — 익명 join이 자리를
되찾게 하면 보안·정합성이 깨진다. 자리 회수는 토큰으로.

## 10. "유예도 프론트 활동으로 갱신해야 하지 않아?" — 연결=활동 신호

**상황.** 위를 고친 뒤 나온 좋은 질문: *"유예 시간도 프론트에서 사용자 행동이 있으면 갱신시켜야 하지 않아?"*

**고민.** 처음엔 앱 레벨 하트비트(주기적 핑)를 떠올렸다. 하지만 **모바일 백그라운드에선 타이머가 얼어**
핑을 못 쏜다 — 정작 필요한 순간에 못 보낸다. 더 중요한 통찰: **연결 자체가 이미 활동 신호**다.
Socket.IO는 ping/pong으로 누가 접속 중인지 실시간으로 안다. 별도 핑을 얹을 이유가 없다.

**해결(3차 — 유예 만료 정책 + 명시적 나가기).**
- **유예가 만료돼도 상대가 아직 접속 중이면 방을 없애지 않는다.** 내가 자리를 지키는 한 계속 기다림.
  **둘 다 없을 때만** 방을 정리. → 내가 화면을 붙들고 있으면 상대가 아무리 오래 백그라운드여도 게임이
  강제 종료되지 않는다. (원한 "활동이 있으면 유지"를, 앱 핑 없이 **접속 상태**로 달성.)
- **의도적 나가기 `leave` 이벤트 신설.** 그동안 "나가기"와 "백그라운드 끊김"이 서버 입장에서 **구분 불가**
  (둘 다 그냥 disconnect)라 "상대 나감"이 애매했다. 이제 나가기 버튼은 `leave`를 쏴 서버가 상대에게
  **즉시** `opponentLeft`를 보내고 방을 정리한다. `backToMenu`는 소켓을 끊지 않고 유지(메뉴 즉시 사용).

**교훈.** "사용자 활동으로 타이머 갱신"이 필요할 때, **이미 있는 신호(연결 상태)를 재사용**할 수 있는지
먼저 본다 — 새 하트비트는 대개 중복이고 모바일에선 신뢰도도 낮다. 그리고 **의도(나가기)와 사고(끊김)를
프로토콜에서 구분**하면 애매한 상태가 크게 준다. 같은 disconnect라도 원인이 다르면 이벤트를 나눠라.

## 부록 — 반복해서 통한 디버깅 습관

- **증상 범위로 원인 층을 좁힌다.** "전부 반영 안 됨" → 파이프라인. "특정 상황만" → 코드 분기.
- **방화벽은 두 층**(클라우드 콘솔 + OS iptables), iptables는 **순서가 로직**.
- **모바일 실시간은 "끊김이 정상"** — 유예·토큰 rejoin·**세션 영속**이 기본 3종.
- **의도와 사고를 이벤트로 구분**(`leave` vs `disconnect`)하면 상태가 명료해진다.
- **서버를 고치면 재배포**를 잊지 않는다: `git pull && pnpm -C server build && pm2 restart nb-server`.
  프론트(Vercel)는 자동, 서버(VM)는 수동 — 이 비대칭을 늘 의식.
